## Title (37 characters; limit 5–50)

Worksight: Few-Shot Visual Inspection

## Short description (202 characters; limit 50–255)

Worksight checks industrial parts against 10–20 photos of good parts: no model training, a defect heatmap in under a second and an AI description from Gemma on AMD. The engineer confirms every decision.

## Long description (1706 characters; limit 600–2000)

Quality engineers lose time when every new part needs a trained defect model and labelled defects. Worksight needs only 10–20 photos of good parts. A frozen ResNet-18 builds a memory of normal image patches in seconds; a new photo gets an anomaly score, a heatmap of unusual regions and the most similar good reference.

The engineer stays in charge. The model decision and the human decision are stored separately. Confirmed-normal parts can build a new profile version, which is activated only if it adds no false positives or false negatives on a frozen validation set, with rollback.

Every flagged part also gets an explanation from Gemma-4-31B-IT running on AMD GPUs through AMD Token Factory. Gemma sees the photo, the heatmap overlay, the closest good reference and the part's own documentation, and tells the engineer what looks wrong and what to check. The detector's decision and score are passed in and never changed, and the report shows which model answered. The detector is PyTorch with ROCm-aware device selection and a one-command AMD benchmark script.

Measured on the VisA PCB set (CC BY 4.0, CPU, held-out test, settings chosen on other categories): AUROC 0.88–0.99, recall 44–87% at a 2–6% false-alarm rate; with the review band, 56–96% of defects reach the engineer while 4–13% of good boards do. 0.1–0.3 s per inspection on Railway CPU. A new part needs no defect labels and no training run: its profile builds in about 9 s from 20 good photos.

A first-visit tutorial, a guided tour, History with batch inspection, report export and seven interface languages make it usable from the first minute. Live demo: web-production-d9743.up.railway.app. Next.js, FastAPI, PyTorch, MIT licence.

## How we use AMD

- **In the product today:** every AI description is generated by Gemma-4-31B-IT served on AMD
  Instinct GPUs through AMD Token Factory. Server errors get two retries before DeepSeek-V4.1-Flash
  (also on Token Factory) answers; the report records which model answered.
- **Detector on AMD GPU:** the PyTorch detector selects a ROCm device and refuses CPU fallback with
  `WORKSIGHT_REQUIRE_AMD=1`. `bash scripts/amd_run.sh` checks ROCm, runs the API smoke test and the
  VisA benchmark with `--require-amd`, and saves GPU name, ROCm version, metrics and latency. Add the
  result here only after a real run.

## Additional information (form field)

Worksight scales by camera view: each part and camera view is a profile built from its own good
photos, so a new product needs no labelling project or training run. The detector is a frozen
encoder plus nearest-patch memory, so serving cost grows with the number of reference patches, not
with model training; the same PyTorch code selects a ROCm GPU on AMD Instinct for higher throughput
(`scripts/amd_run.sh` measures it). Engineer feedback is immutable and every profile change passes a
measured gate on a frozen validation set before an explicit activation, which keeps updates auditable
across lines and shifts. Explanations come from Gemma on AMD Token Factory and never change the
detector's decision. Next: batch and stats screens (API ready), an edge station on AMD Ryzen AI and a
pilot on one production line.

## Claims we do not make

- The detector has not run on an AMD GPU yet; hosted inference is CPU (`runtime.amd_gpu: false`).
- No model was trained; this is a PatchCore-inspired baseline, not a PatchCore reproduction.
- The anomaly score is not a probability. Metrics are VisA PCB on CPU only (`docs/BENCHMARK.md`).
- Sensor monitoring, failure forecasting and PDF specification extraction are not implemented.
